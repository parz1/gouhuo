## 红线为什么拆成两组

第一版是一组「破线算 bug、松一次就回不去」的数字：端到端 80 ms、CPU 3%、
说话带宽 40 kbps。M2 测完发现端到端 91.9 ms，破线 11.9 ms。

但真正该问的不是「怎么把 91.9 压到 80」，而是「91.9 ms 用户能不能接受」——
答案是能：ITU-T G.114 把单向嘴到耳 150 ms 划为「用户很满意」的上界，
Discord / TeamSpeak 在同类配置下普遍 100–150 ms。**那条 80 ms 本身没有依据。**

更糟的是 40 kbps 那条：它跟延迟直接打架。M1 实测 10 ms 帧要 61.3 kbps，
于是「延迟要 10 ms 帧、带宽要 20 ms 帧」成了死结，把包头瘦身从优化项变成了
阻塞项。放开之后死结自己没了。

**两条教训**：一是别把「防止倒退」和「对用户的承诺」混成一组数字；
二是红线之间会互相打架，定的时候要一起看。

## M1 结论

**GO —— 但帧长这个旋钮上出现了一个必须解决的冲突：延迟要 10 ms 帧，带宽要 20 ms 帧。**

完整报告存档在 [`docs/m1-baseline.txt`](docs/m1-baseline.txt)，下面的数字都出自那一份。

测法：不接音频设备，喂合成信号打时间戳，走完整的
「Opus 编码 → 加密 → UDP → 服务端转发 → 抖动缓冲 → 解码 → 播放」链路。
拿到的是不掺设备延迟的干净数字，也就是这套架构的物理下限。

延迟同时用两套**互相独立**的方法量，对得上才算数：

1. 墙钟：播放时刻 − 采集时刻，加一帧（渲染侧摊开）加 Opus 前瞻
2. 信号域：拿播出的 PCM 跟参考信号做归一化互相关，直接量波形延迟

两者在所有配置下都对到 0.1 ms 以内。任何一次测量对不上账，报告里会直接标
「别信这一行」。

### 主要数字

测试机：AMD Ryzen 7 5700X3D（8C16T）/ Windows 11 Pro / rustc 1.96 MSVC / release 构建。
网络档 `city` = 单程 12 ms、抖动 σ=4 ms、丢包 0.5%（客户端→服务端→客户端两跳合计）。

| 帧长 | 缓冲深度 | 协议嘴到耳 p95 | 欠载 | 判定 |
|---|---|---|---|---|
| 10 ms | 1 帧 | 46.6 ms | 1 | 延迟够但音质不行 |
| **10 ms** | **2 帧** | **46.5 ms** | **0** | **可用** |
| 10 ms | 3 帧 | 56.6 ms | 0 | 音质够但超预算 |
| 20 ms | 2 帧 | 66.5 ms | 0 | 音质够但超预算 |
| 20 ms | 3 帧 | 86.6 ms | 0 | 音质够但超预算 |

80 ms 的预算里，协议部分占 46.5 ms，**还剩 33.5 ms 给 WASAPI 采集 + 渲染**。

延迟各项的量级（10 ms 帧 / 缓冲 2 帧 / city）：

```
打包（一帧攒满才能编）        10.00 ms
Opus 编码器前瞻               6.50 ms   <- 编码器自报，互相关能对上
编码 p95                      0.26 ms
网络（两跳合计）             12.00 ms
服务端转发 p95                0.05 ms   <- 转发器就是个 UDP 中继，几乎不要钱
抖动缓冲（2 帧）             20.00 ms
解码 p95                      0.06 ms
渲染侧摊开一帧               10.00 ms
```

**这几项不是加法。** 包在网上飞的时候缓冲也在填，两段是重叠的。真正成立的是：

```
墙钟   ≈ 网络单程 + (缓冲深度 − 1) × 帧长 + 采集/播放两个时钟的相位差(0 ~ 一帧)
嘴到耳 = 墙钟 + 一帧（渲染侧摊开）+ Opus 前瞻
```

代进去：`12 + 10 + ~8 = 30.0` 墙钟，`30.0 + 10 + 6.5 = 46.5` 嘴到耳。实测 46.5。

**编解码加起来 0.32 ms，服务端转发 0.05 ms。** 自研传输这个决定在延迟上完全成立 ——
协议栈本身根本不是瓶颈，抖动缓冲和帧长才是。

### 三个必须记住的发现

**1. 帧长的取舍是「延迟 + CPU」对「带宽」，不是三者对一者。**

| 帧长 | 每包固定开销 | 固定开销折算 | Opus 16k 时说话带宽 | 编解码 CPU |
|---|---|---|---|---|
| 10 ms | 57 B | 45.6 kbps | 61.3 kbps | 2.18% |
| 20 ms | 57 B | 22.8 kbps | 39.0 kbps | 2.75% |

固定开销 57 字节 = IP/UDP 头 28 + 我们的包头 13 + AEAD tag 16。
**10 ms 帧下，还没编码一个比特，固定开销就已经 45.6 kbps，40 kbps 的红线当场破。**

反直觉的是 CPU：10 ms 帧**更省**。Opus 单帧编码成本随帧长超线性增长
（20 ms 一帧 481 µs vs 10 ms 一帧 190 µs，2.5 倍不是 2 倍），按秒摊反而短帧便宜。

这个冲突必须在 M3 解决，可动的地方（都还没做）：

- 包头 13 → 7 字节：`timestamp` 在定长帧下可由 `seq` 推出，`session` 用 u16
- AEAD tag 截短到 8 字节（SRTP 的常规做法）
- Opus 码率降到 16 kbps

三条加起来在 10 ms 帧下能省约 21 kbps，刚好把 61.3 压到红线内。
在做完这个之前，10 ms 帧只是「延迟上可行」，不是「可以发布」。

**2. 固定抖动缓冲每欠载一次，延迟就阶梯式上涨，而且再也不下来。**

表里 `10 ms / 缓冲 1 帧` 的延迟跟 `缓冲 2 帧` 一模一样（46.6 vs 46.5），就是这个原因：
它欠载了一次，重新预缓冲，攒到的深度就回不去了。所以「把缓冲调浅」在固定缓冲上
根本换不到低延迟，只换到一次听得见的卡顿。

这正是[自适应抖动缓冲（M4）](#路线图)要解决的问题，也是「没法一边把低延迟当卖点，
一边用别人给通用场景调的缓冲策略」这句话的实证。

`bad` 档（抖动 σ=15 ms）下，缓冲 1 帧欠载 4 次、听感丢帧 7.8%；
要压到 0 次欠载得把缓冲加到 2 帧，代价是延迟涨到 76.5 ms。

**3. Windows 上有两个会默默吃掉语音包的坑，都已经修在 `voice-core::net` 里。**

- **不要用 `SO_RCVTIMEO` 轮询退出标志。** Winsock 的读超时跟正在到达的数据报
  撞车时会把整个数据报丢掉。读超时周期一旦接近帧间隔就会周期性撞上：
  20 ms 超时 + 20 ms 帧在**纯回环、零网络损伤**的链路上稳定丢约 0.5%，
  同一份代码换成 10 ms 帧一个不丢。抓包工具里看不见，只表现为「偶尔咔哒一下」。
  正确做法是一直阻塞在 `recv_from` 上，用哨兵包唤醒。
- **UDP 默认接收缓冲只有 8 KB。** 收包线程被调度器晾一下，或者七八个人同时说话，
  缓冲就满了，内核默默丢包不报错。

还有一个不是 bug 但同样致命的：Windows 默认定时器粒度 15.6 ms，
`sleep(20ms)` 实际可能睡 31 ms。必须 `timeBeginPeriod(1)` 加自旋收尾，
见 `voice-core::clock`。

### 这些数字**不**包括什么

不写清楚就是自欺欺人：

- WASAPI 采集 + 渲染延迟（M2，这是 80 ms 里最后一块拼图）
- APM（AEC3 / 降噪 / AGC）的延迟与 CPU。AEC3 是这条链路上最贵的一块
- 真实公网的抖动分布 —— 这里用的是高斯，真网络是重尾的
- 多人同时说话时服务端转发的扇出开销
- 下行带宽：K 个人同时说话就是 K 倍，红线只管住了单条上行
- 内存和安装包红线

另外，延迟矩阵里采集和播放两个时钟的相位差被刻意钉在了最坏的一端
（为了让互相关的滞后一定为正），所以表里的数字比真机平均值**偏高约半帧**。

预算里那 30 ms 的设备额度是**假设不是实测**，依据是共享模式下采集和渲染各约一个
10 ms 引擎周期加混音器一跳。M2 的第一件事就是把它换成实测值。

## M2 结论（设备部分）

**设备吃掉 30.4 ms。端到端 76.9 ms，进线 —— 但余量只剩 3.1 ms，而 APM 还没接。**

完整报告存档在 [`docs/m2-baseline.txt`](docs/m2-baseline.txt)。

测法：真开 WASAPI 流，但**不出声**。渲染全程灌静音；采集不需要麦克风前面有声音 ——
`IAudioCaptureClient::GetBuffer` 的 `pu64QPCPosition` 就是「这一包第一个采样点被设备
记录下来的那一刻」，跟我们拿到手的时刻一减就是采集延迟。

| 路径 | 实测 | 是什么 |
|---|---|---|
| 采集 | 10.37 ms | 一个引擎周期。WASAPI 时间戳直接量到的，没得选 |
| 渲染 | 20.00 ms | 我们维持的队列深度。**这是设计选择，不是物理限制** |

### 渲染那 20 ms 是一个可以翻案的决定

渲染的物理下限是 **10.02 ms**（一个周期多一帧），实测五秒零欠载。
但那个工作点的余量只有**一帧** —— 线程漏醒一次就是一声咔哒，而这软件是要跟游戏
抢 CPU 的。取 20 ms 是为了留住整整一个周期的余量，扛得住漏醒一次。

想换回 10 ms 也行：那是拿「偶尔咔哒」换 10 ms 延迟，端到端会从 76.9 掉到 66.9。
这是产品决定不是技术决定，所以摆在这儿，不藏在代码里。

### 三个发现

**1. `IAudioClient3` 的低延迟共享模式在这台机器上没有红利。**

Win10 之后共享模式也能把引擎周期压到驱动支持的最小值，不用走独占。但这台机器上
所有真硬件端点报的 `engmin` 都等于 `engdefault`（10 ms）—— 驱动不配合，这条路是空的。
讽刺的是虚拟声卡反而报 2 ms，因为它不是真硬件，可以随便报。

**2. 独占模式不能用，而且这台机器上根本没测起来。**

独占能把周期压到 3 ms，但独占期间**游戏本身发不出声** —— 开黑软件不可能用它。
本来只想拿它标定上限，结果渲染路径报
`AUDCLNT_E_BUFFER_SIZE_ERROR`，采集路径的时间戳又恒等于 0。所以这条只留了个能跑的
代码路径，没有可信数字。

**3. 默认端点是虚拟声卡，而虚拟声卡的延迟测不准。**

这台机器的默认收发端点都是 SteelSeries Sonar —— 这在中国玩家里极其常见
（Sonar、雷蛇 Synapse、Voicemeeter、直播软件的虚拟线）。它们是用户态音频路由，
在真硬件之上再叠一层。

麻烦的是它们测出来**比真硬件还低**（采集 0.42 ms vs 硬件 10.37 ms）。那不是更快，
是这种量法测不到它的上游：虚拟设备自己造 QPC 时间戳，只覆盖「路由把数据递给我们」
那一段。所以探针里加了一条判据：**采集延迟小于四分之一个周期就判定时间戳不可信**
（音频物理上至少要攒够一个周期才可能交付），不可信的一律不进预算。

真实用户的延迟 = 硬件那一层 + 虚拟声卡那一层，只会比 30.4 ms 更高。这一层目前测不到。

### APM：AEC3 吃掉 15 ms

用 [`sonora`](https://github.com/dignifiedquire/sonora) —— libwebrtc
AudioProcessing 模块（M145）的**纯 Rust 移植**。不需要任何 C++ 工具链。

M2 时用的是 C++ 的 `webrtc-audio-processing`（M131）：它在 Windows/MSVC 上
开箱编不过，我们打了七个补丁、vendor 了 5.3 MB 源码、写了个环境准备脚本才跑起来，
而最贵的代价是 **APM 因此默认关着**。2026-09 换成纯 Rust 之后那些全没了，
APM 现在是默认开的。换之前做了 A/B，数字和它的局限见
[`docs/apm-backend.md`](docs/apm-backend.md)。

逐块计价（10 ms 帧，近端 + 远端两次调用）：

| 配置 | CPU | 延迟 |
|---|---|---|
| 全关（基线） | 0.01% | 0.00 ms |
| 只开 AGC2 | 0.03% | 0.00 ms |
| 只开 高通 | 0.21% | 0.92 ms |
| 只开 降噪 | 0.27% | 6.92 ms |
| 只开 AEC3 | 0.71% | 8.92 ms |
| **全开（实际配置）** | **0.79%** | **14.92 ms** |

延迟是互相关量出来的（APM 不自报这个数），并且用**冲激法独立验过一遍** ——
整条红线过不过压在这个数上，一种量法不够。

**AEC3 和降噪占了 APM 全部 15 ms 里的绝大部分**，而这两块都不是可选的：
没有 AEC3 外放开黑就啸叫，没有降噪机械键盘声直接糊到队友耳朵里。
放开产品线之后这 15 ms 是买得起的 —— 详见下一节。

顺手量到一件事：APM 强制 **10 ms** 处理帧（`audio_processing.h:83`）。
打包粒度不受影响，20 ms 一个包跑两次 APM 即可 —— 不改变 M1 的帧长结论。

### 端到端 91.9 ms

APM 那一段实测 14.92 ms，但 `APM_BUDGET_MS` 取整到 **15.0** —— 预算不该追第三位
小数，而且取整的方向是保守的那一边。下面的合计用的是预算值，跟
`redline::MEASURED_E2E_MS` 完全一致。

```
协议链路   46.5 ms   （M1：10 ms 帧 + 缓冲 2 帧 + 同城两跳）
设备       30.4 ms   （M2：采集 10.4 + 渲染队列 20.0）
APM        14.9 ms   （AEC3 + 降噪 + AGC2 + 高通）
--------------------
合计       91.9 ms   产品线 120 ms，防回归闸 100 ms
```

在产品线内，而且比 Discord / TeamSpeak 同类配置（普遍 100–150 ms）要好。

**更重要的是：所有该选的安全选项现在都买得起了。** 之前为了挤进 80 ms，
下面这些取舍每一个都被迫要重新考虑；现在一个都不用动：

| 选择 | 代价 | 现在 |
|---|---|---|
| 渲染队列 20 ms（而不是 10） | +10 ms | **保持** —— 留住一个周期的余量，扛得住线程漏醒一次 |
| 抖动缓冲 2 帧（而不是 1） | +10 ms | **保持** —— M1 实测 1 帧会欠载，延迟还会阶梯式涨回去 |
| 降噪开着 | +7 ms | **保持** —— 关掉的话机械键盘声直接糊到队友耳朵里 |
| AEC3 开着 | +9 ms | **保持** —— 关掉外放就啸叫 |

还想更快的话，最便宜的一档是渲染队列压到 10 ms（省 10 ms，端到端到 81.9），
代价是余量只剩一帧、线程漏醒一次就是一声咔哒。**现在没有理由换** ——
省下来的 10 ms 买不到任何用户感知得到的东西，而咔哒是听得见的。

真正该继续压的地方在协议链路那 46.5 ms 里：抖动缓冲占 20 ms，
而那是固定缓冲的代价。当时的预期是自适应缓冲能在同样的音质下把它压下去 ——
**M5 实测没有**：同城档下自适应自己也选了 2 帧，数字一样。它的收益在别处，
见 [M5](#m5-结论自适应抖动缓冲)。

### 这些数字**不**包括什么

- **真回声下 AEC3 消得干不干净。** 测延迟和 CPU 时远端喂的是静音，没有回声可消。
  效果好不好要真声学环境才测得了
- 声学往返（音箱 → 空气 → 麦克风）。要出声，得单独做
- 虚拟声卡那一层、蓝牙耳机（那是另一个量级，编解码器本身就几十毫秒）
- 采集和渲染两个时钟不同步时的重采样代价

数字来自一台机器：Ryzen 7 5700X3D + Arctis Nova Pro Wireless（USB）+ Realtek，
共享模式引擎周期 10 ms。

## M5 结论：自适应抖动缓冲

### 问题

固定缓冲（2 帧）在网络卡一下之后，延迟**永久**涨上去：缓冲被抽空 → 退回预缓冲、
从缓冲里最早的一帧重新对表 → 之后每个包都在缓冲里多等那么久，再也不下来。
一直在说话（或者一直按着说话键）的时候，卡几次就是几级台阶。

### 做法

实现在 `voice-core` 的 `jitter`、`playout`、`timescale` 三个模块，文档写在模块头里。一句话版：

- **目标深度从到达时间里算**：相对迟到（减去最近 2 秒最小传输延迟）的 97% 分位
- **缓冲空了停下来等**，用 PLC 顶上，不重新对表
- **延迟多出来就加速播**：一口气解 30 ms，删掉一个基音周期（2.5–15 ms，
  交叉淡化，音高不变），一直收到只多出不到 1/4 帧

### 验收：抖一小时，延迟回到起点

实时跑一小时不现实，而且每次都不一样。所以写了一个离线模拟器（`voice_core::netsim`）：
虚拟时钟、有种子的随机数，播放逻辑就是线上那一份，固定和自适应吃**同一串**到达时刻。
一小时两秒钟跑完：

```
cargo run --release -p latency-probe -- sim
```

同城（单程 12 ms，σ=4 ms，丢包 0.5%），每分钟卡一次 200 ms，夹三段一分钟的烂网络（σ=15 ms）：

| 场景 | 缓冲 | 首分钟 | 末分钟 | 平均 | p99 | 没播出 |
|---|---|---|---|---|---|---|
| 一直在说，1 小时 | 固定 2 帧 | 30.4 | **220.4** | 217.2 | 220.4 | 0.50% |
| | 自适应 | 33.1 | **38.2** | 38.0 | 160.4 | 0.57% |
| 说 4 秒停 3 秒，1 小时 | 固定 2 帧 | 30.2 | 28.8 | 38.3 | 220.4 | 0.70% |
| | 自适应 | 30.9 | 30.8 | 35.4 | 157.0 | 0.61% |
| 局域网，10 分钟 | 两个一样 | 20.4 | 20.4 | 20.4 | 20.4 | 0 |

每 5 分钟的平均：固定 `182 220 220 …`，第一次卡完就上了台阶再没下来；
自适应一整个小时在 36–41 之间。好网络上两者完全一样，自适应没有白白加深。

说说停停的时候固定缓冲也不怎么涨 —— 句间停顿会把它重置。台阶只在「一直在说」时出现，
但那正是按住说话键不放、或者 `TransmitMode::Always` 的情形。

延迟的定义：发送端采到这一帧 → 它的第一个采样开始播。不含声卡、APM、编码前瞻。

### 实时对照：短时间里两者差不多

同一套播放器接进了 latency-probe（`--adaptive`），真 Opus、真 UDP、真线程、网络仿真、
服务端转发一跳，10 ms 帧，每档 20 秒：

| 档位 | 缓冲 | 嘴到耳 p95 | 迟到丢弃 | 结束时自适应的目标 |
|---|---|---|---|---|
| city | 固定 2 帧 | 46.6 | 0 | — |
| | 自适应 | 46.6 | 0 | 2 帧 |
| bad（σ=15 ms，丢包 3%） | 固定 2 帧 | 66.6 | 51 | — |
| | 自适应 | 71.3 | 56 | 5 帧 |

**20 秒里看不出自适应的好处**，bad 档甚至高了 4.7 ms：它从一开始就按 5 帧起播，
而固定缓冲是欠载了一次、被台阶推到了差不多的深度。区别在时间尺度上 ——
固定缓冲接下来每卡一次都可能再上一级，自适应会还回去。这正是上面那张一小时的表。

CI 卡的协议延迟（46.5 ms）量的还是固定缓冲，这部分逻辑一行没动。

### 三个发现

**盯缓冲水位不行，要盯延迟。** 第一版在「缓冲里攒的帧数比目标多一帧」时加速。
水位本身跟着到达抖动在跳，只能留一帧余量，结果每次卡完都停在余量的上沿：
十分钟的同城场景里，从 31.6 ms 卡到 48.6 ms 就不再下来。改成盯播放延迟
（现在 − 这一帧的发送时刻）：播放时钟是均匀的，所以它只在停着等和加速时才变，
而它的目标就是起播时用的那个数。改完 38 ms。

**不能拿序号当发送时刻。** 发送端不说话时不发包，序号也不涨；停顿之后的第一个包
会被当成迟到了整整一个停顿。要用包头里的采样时间戳（每采一帧都加），
而且要自己解开 u32 的回绕 —— 48 kHz 下 24.8 小时绕一圈，「一挂几小时」的场景真会碰上。

**模拟器里的对照组必须真的会坏。** 第一次写的测试里，固定缓冲「没涨」——
因为测试驱动把还在路上的包提前塞进了缓冲。按到达时刻投递之后，
固定缓冲才从 30 ms 涨到 240 ms。这条测试现在留着当对照：它不坏，说明模拟器是错的。

### 这些数字**不**包括什么

- **真网络的抖动分布。** 模拟器是高斯 + 人为的尖峰，真网络是重尾的
- **真人声的加速效果。** 模拟器的假解码器出的是纯周期信号，每次都能删；
  真人声里清辅音和噪声段不删，还债会慢一些。听感没做主观测试
- **目标变深时的平滑过渡。** 网络突然变差时，延迟是靠「停着等」（PLC）涨上去的，
  没有做反向的减速播放（WSOLA 的 expand），那几帧 PLC 是听得出来的
- **编码器的 FEC 力度**还是写死按 10% 丢包率开的，没按接收端实测丢包率调。
  要调得把接收端的丢包率反馈回发送端，那是另一件事

## M6：客户端的内存和后台开销

### 为什么要分状态量

篝火真正的用法是进游戏之后丢在后台挂几个小时，窗口在前台的时间反而短。所以
「最小化挂着」「收在托盘里」才是最要紧的状态，只量一个开着窗口的数不够。
后台挂着时，CPU 和**唤醒次数**跟内存一样要紧：那是跟游戏抢调度的东西。

### 量法

```
.\scripts\m6-footprint.ps1 -Seconds 60              # 四个状态各 60 秒
.\scripts\m6-footprint.ps1 -Seconds 60 -LongMinutes 48   # 再收在托盘里挂 48 分钟
.\scripts\thread-wakeups.ps1 -ProcessId <pid>       # 按线程名列出谁醒得多
```

- dist profile；本机起一个服务端
- 频道里有一个「说话机器人」（`client-core/examples/talker`）一直在发声，客户端要真的
  在解码、混音、过抖动缓冲。机器人的音量在客户端设置里调成 0（单人音量）：解码和混音
  照常，只是不从音箱里出声
- 工作集和私有字节都记：前者是任务管理器默认显示的，后者是真正占着的
- 唤醒 = 所有线程每秒被切上 CPU 的次数，用 WMI 的原始线程计数器算差值
  （性能计数器的路径在中文 Windows 上是本地化的，写死英文名会找不到）

### 结果

| 状态 | 工作集 | 私有字节 | CPU（单核） | 唤醒 / 秒 |
|---|---|---|---|---|
| 登录页空闲 | 60.2 MB | 49.5 MB | 0.00% | 5 |
| 在频道里，前台 | 73.0 MB | 57.0 MB | 1.5–2.3% | 414–416 |
| 在频道里，最小化 | 73.0 MB | 56.8 MB | 1.3–2.0% | 389–401 |
| 在频道里，收在托盘 | 72.9 MB | 56.8 MB | 1.4–2.0% | 363 |

CPU 给的是两轮的范围：轮与轮之间差 0.5 个点左右，比状态之间的差别还大。
登录页的唤醒在窗口收到鼠标、焦点事件时会多一些（长测那一轮是 54），单独量两次都是 5。

收在托盘里挂 48 分钟，每分钟一个点：

| | 首 | 末 | 最低 | 最高 |
|---|---|---|---|---|
| 工作集 | 73.0 | 73.3 | 73.0 | 73.4 |
| 私有字节 | 56.7 | 56.7 | 56.7 | 56.8 |

私有字节前一半平均 56.71、后一半 56.70：没有泄漏，也没有只涨不降的缓冲。
工作集开头那 0.3 MB 是页面陆续调进来，之后不再动。计划是两小时，跑到 48 分钟
数据已经完全平直，手动停了 —— 更慢的泄漏（每小时几百 KB 那种）要更长的测试才看得出来，
这次没覆盖。

**对红线**：voice-core 常驻内存 < 100 MB。整个进程（含界面）在频道里 73 MB，
语音那一半约 13 MB（减掉登录页的 60 MB）。离线很远，不用把 voice-core 拆成独立进程。

### 三个发现

**最小化时 Windows 并没有裁剪工作集。** 当初以为它会裁（那样工作集会掉得很好看，
私有字节不变），所以特意两个都记。实测三种状态工作集差不到 0.2 MB。
两个都记的做法留着，结论改了。

**界面线程不管窗口在不在都每秒醒 190 次。** 按线程名一列就看出来了：登录页空闲时
全进程只有 `main` 在动，190 次 / 秒。两个界面定时器 —— 20 ms 查按住说话的键、
50 ms 同步电平条和说话指示 —— 窗口看不见照样跑，每次还要带出两三次额外的唤醒。
改成：

- 窗口看不见（最小化、托盘）或者没什么在动（登录页）时，界面同步放慢到 500 ms，
  只管托盘图标，顺便发现窗口被恢复了、切回 50 ms
- 按住说话的定时器只在真用得着时跑（连着、而且是按住说话模式；或者正在绑键）。
  收在托盘里用按住说话打游戏时照跑 —— 那正是它最要紧的时候

改完登录页空闲 236 → 5 次 / 秒，频道里后台约 620 → 约 370。剩下的是语音那几个线程
（采集、播放、收包各约 100 次 / 秒）：10 ms 一帧，省不掉。**CPU 没因此降多少** ——
大头是解码和回声消除，后台照样得跑。

**UI 自动化会把量出来的数撑大。** 第一轮用 UI 自动化点「关耳朵」让测试音别出声，
结果在频道里的工作集多了 8 MB、线程多了好几个：一旦有 UI 自动化客户端来访问，
界面的无障碍支持就被激活，而且一直开着。普通用户没开读屏软件时不会有这部分。
所以测量脚本全程不碰 UI 自动化，改用单人音量让机器人静音。

### 这些数字**不**包括什么

- **多人同时说话。** 只有一个说话机器人。N 个人同时说话是 N 路解码
- **显卡那边的内存**（纹理、OpenGL 上下文）。进程的私有字节不含驱动在显卡上分配的
- **跟真游戏一起跑时的帧时间影响。** 那是 #12
- **更慢的泄漏**：见上面，只挂了 48 分钟

## 篝火动画的开销

右边那堆像素篝火，火苗每 100 ms 画一帧。问题只有一个：它会不会把「挂一晚上不占资源」
打破。

### 什么时候动

| 窗口的状态 | 火 |
|---|---|
| 在前台 | 10 帧 |
| 不在前台，也没被盖住（比如放在副屏上） | 4 帧 |
| 前台是铺满同一块屏幕的全屏程序（在打游戏） | 停 |
| 最小化、收在托盘、切到文字聊天、窄窗口时看着频道树 | 停，定时器也停 |
| 系统设置里关了「动画效果」 | 停，只画一帧 |

最常见的用法是「开着篝火、进游戏」：窗口没最小化，只是被全屏游戏整个盖住。
所以要专门看前台是不是全屏程序 —— 只看「窗口可见 / 最小化」的话，这时火会一直烧。

### 量法

release 版，本机服务端，频道里两个**不说话**的机器人（`talker --silent`）。
第一次带着两个说话的机器人量，同一个状态两轮之间差 1–2 个点，跟要量的差别一样大 ——
解码和混音的噪声把火的开销淹没了。机器人不说话之后，轮与轮之间差 0.5 个点左右。

窗口 760×520、在前台，每个状态 20 秒，量两轮。为了拆开开销，临时加过两个开关
（量完删了）：「不画，轮流贴 10 张画好的图」和「画，但不交给界面」。

| 状态 | 第 1 轮 | 第 2 轮 |
|---|---|---|
| 火关掉 | 1.88% | 1.25% |
| 火正常动 | 3.36% | 3.44% |
| 不画，只换图 | 2.97% | 3.59% |
| 画，不换图 | 1.48% | 1.95% |

另外按窗口状态量了一轮（说话机器人在，噪声大，只看趋势）：前台 6.04%、
前台是一个普通小窗口 5.10%、前台是全屏窗口 2.81%（跟火关掉一样）。
帧率另外打日志确认过：前台 10.0 帧，切走之后 4.0 帧。

### 结论

**火在前台时多花约 1.8% 单核，几乎全是界面重画整个窗口的钱。** 画像素本身
（125×118 格）一帧 0.57 ms，火苗前后那两层每 3 帧才重画一次；
换成 Skia、femtovg、软件渲染量出来都差不多，所以不是哪个渲染器慢，是每帧整窗重画。
要再省只能降帧率。

打游戏时（全屏盖住、最小化、托盘）火一帧都不画，定时器也停着，**后台开销跟没有这个功能一样**。

### 这些数字**不**包括什么

- **全屏检测只拿一个铺满屏幕的无边框窗口试过**，没拿真游戏试。独占全屏的游戏
  前台窗口也是铺满屏幕的，应该一样，但没验证
- **副屏上 4 帧**时的 CPU 没单独量干净（只有上面那组带噪声的数）
- 显卡那边的开销（贴图上传、合成）不在进程 CPU 里

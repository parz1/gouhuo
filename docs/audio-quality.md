# 音质修复与验收（issue #35）

## 2026-10-01：针对“发闷、像电话”的第二轮修改

当前默认是 **48 kHz、单声道、64 kbps、10 ms、Opus Audio + Auto、复杂度 5**。
APM 配置沿用第一阶段；FEC/DTX 仍开启，接收仍使用原来的 PLC 路径。
Audio 模式优先原声保真，Auto 允许编码器按输入选择模式；不强制锁定 CELT，
也不把启用 FEC 等同于接收端已经恢复丢包。

对标资料（2026-10-01 查阅）：

- [KOOK 官方频道权益](https://help.kookapp.cn/f0fa/c59e)：普通服务器上限 64 kbps，
  助力档位最高 128/192/256/320 kbps。这是频道上限，不是每个人实际发送码率。
- [KOOK 官方语音接口](https://developer.kookapp.cn/doc/http/voice)：公开的机器人语音
  推流使用 Opus；这不能证明所有客户端的完整内部参数。
- [Oopz 设备说明](https://help.oopz.cn/42f9/c43a)确认最高支持 48 kHz；
  [频道设置](https://help.oopz.cn/42f9/3020)提供码率/延迟选项，未公开完整算法配置。
- [Opus 官方 CTL 文档](https://opus-codec.org/docs/opus_api-1.5/group__opus__encoderctls.html)
  区分 VoIP 的语音可懂度取向与 Audio 的原声保真取向。

原先 80 kbps 的 IPv4 上行预算容不下 64 kbps 编码加 45.6 kbps 固定开销。
本轮随音质目标将预算改为 120 kbps；不改变 10 ms 帧长和延迟红线。
尝试复杂度 8 时，旧 VoIP + Voice 探针测得一路编解码中位耗时占单核约 6.01%，
尚未包含 APM，所以最终保留复杂度 5。这个探索值不能用于宣称最终配置 CPU 达标。

语音激活新增 200 ms 尾音保护，短暂停顿和低电平尾音继续发送；闭麦、松开 PTT
和切到 PTT 模式立即生效。它不增加持续讲话的播放缓冲，但会多发最多 200 ms 尾部音频。
尚未增加开口预录，不能声称已解决所有首字截断。

最终配置的合成诊断：`target/quality-hd-final-clean` / `target/quality-hd-final-loss5`。
命令沿用下文，更换输出目录；现在扫描 24/32/48/64 kbps 四档，其他配置均为当前线上值。
全开 APM、64 kbps 下，500 个输入包全部为 Fullband（编码频带标签），
编码实测 64.110 kbps、含 IPv4 上行 109.710 kbps、前瞻 312 点（6.5 ms）。
干净网络没有 PLC、等待、加速或输出削波；均匀 5% 丢包删除 27 包，46 次 PLC、
20 次等待，无加速或输出削波。末尾等待问题仍未解决。

报告新列 `codec_mean_cpu_percent` 计时线上编码器和一路直接解码，跳过前 200 ms，
排除 APM、网络和播放。该合成信号 release 运行测得 3.274%（干净）/3.196%（丢包扫描），
不能用它代替全客户端、多人语音或真人输入的 CPU 验收。
新增高频回归测试同时检查包频带和解码后的 12 kHz 分量：保留至少 20% 输入幅度，
且超过旧 32 kbps/VoIP/Voice 配置的 1.5 倍；这是防频带倒退测试，不是听感评分。

语音内核 136 项及完整 TLS/UDP/Opus 链路 15 项测试通过，硬件测试未执行。
**尚未证明听感达到 Oopz/KOOK**：仍需同一麦克风、同音量的真人盲听、真实双机及
真实网络验收。不能拿码率、包频带标签或合成 SNR 替代这个结论，#35 继续保持待验收。

## 第一阶段记录（以下参数与结果为历史配置）

2026-09-30：第一阶段已实现，真人盲听、真实设备嘴到耳测量尚未完成。
本页的频带和信号指标是诊断证据，不是主观音质评分。

## 本次变更

- 混音原先在 `|x| > 0.7` 时突然切换到 `tanh(x)`，正阈值附近输出从
  0.7 跳到约 0.604。现在低电平保持原样，超阈值采用
  `sign(x) * (0.7 + 0.3 * tanh((|x| - 0.7) / 0.3))`，幅度及斜率连续。
  不增加前瞻缓冲。它仍会压缩大信号，不能修复麦克风输入端已经发生的削波。
- AGC2 显式开启自适应数字增益：最大 20 dB、初始 0 dB、变化上限 3 dB/s。
  原先 `GainController2::default()` 的自适应控制器为 `None`，固定增益为 0 dB。
  测试验证数字静音保持静音，安静的合成谐波输入可获得可测增益且不削波；
  真人轻声、键盘及风扇底噪仍需实录验收。
- 默认 Opus 码率从 24 改为 32 kbps，作为待盲听验收的候选。
  `VoiceEncoder::with_bitrate` 可对比 24/32/48；48 kbps 尚未增加客户端设置入口。
  保持 48 kHz 单声道、10 ms、VoIP、复杂度 5、FEC/DTX 配置不变。
- 历史 61.3/39.0 kbps 属于 16 kbps 编码；当前固定 IPv4 开销为
  `(13 + 16 + 28) * 8 * 100 = 45.6 kbps`。保留完整 AEAD tag。
  新 AGC/码率配置不能沿用历史 CPU、APM 延迟及声学验收数字。

## 可复现的 WAV 对比

```powershell
# 仅用于验证工具、频带选择和接收链路，合成音不是主观音质样本。
cargo run --release -p voice-core --example quality-probe -- --synthetic target/quality-clean
cargo run --release -p voice-core --example quality-probe -- --synthetic target/quality-loss5 5

# 真人录音：标准 RIFF WAV，PCM16、单声道、48000 Hz。
# 拒绝其他采样率/声道，避免隐式重采样掩盖问题。
cargo run --release -p voice-core --example quality-probe -- reference.wav target/quality-speech
```

Windows 若缺 cmake，用 `scripts/win-buildenv.ps1 -Run '上面的命令'`。
输出目录的父目录必须存在，输出目录必须是新的，防止覆盖参考录音。
录音不会上传；输出在被 Git 忽略的 `target/` 中。

每次扫描三档码率 × 三种 APM（全关、只 AEC、全开），输出：

- `raw.wav`：原始输入。
- `<apm>-<bitrate>-apm.wav`：采集处理结果，尾部补 400 ms 静音以排空状态。
- `...-codec.wav`：无网络损伤的 Opus 直接解码结果，用于隔离编码问题。
- `...-received.wav`：同一批编码包经过线上使用的 `Playback`（自适应抖动缓冲、
  解码、PLC、时间伸缩）及混音限幅后的结果，额外保留 300 ms 播放排空时间。
- `report.csv`：包的实际频带分布、编码带宽、含 IPv4 头部的发送带宽预算、
  Opus 前瞻、分段 SNR、APM/接收 RMS 与峰值及削波点数、丢包/PLC/等待/加速次数。

WAV 输出采用 IEEE float32，保留超过满刻度的采样供失真诊断，不在导出时偷偷截幅。
文件保留各阶段固有延迟，不直接按样点对齐试听。分段 SNR **仅比较 APM 后与直接
Opus 解码**，去掉编码器报告的前瞻，不做增益归一化；静音帧排除，10 ms 分段，
每段限制为 -10～35 dB，全静音结果为 NaN。它不评价丢包输出，不代表 MOS。
RMS/峰值统计覆盖整个对应输出文件（含尾部），跨阶段 RMS 会受长度影响。
频带标签来自包头，表示编码频带选择，不等同于测得的频响截止或频带能量。

接收模拟为固定单程 12 ms、每 10 ms 调度一次、可靠终止包。
可选丢包用累计百分比确定性均匀删除（5% 约每 20 包丢一个，包含排空段）。
它不模拟突发丢包、到达抖动、乱序、真实 UDP/加密、声卡或发送端的 VAD/DTX 发包抑制。
编码器沿用线上 10% 预期丢包配置；接收端沿用当前 PLC 路径，不将输出误称为 FEC 恢复。
AEC 的参考是静音，无声学回路，不能验收外放回声消除。
带宽统计覆盖输入对应的帧，排除补入的排空段，包含原输入中的停顿，
按照每帧发包计算，IPv4 不含链路层、IPv6、TLS 控制及保活流量。

## 第一轮结果

命令与上面相同，输出目录 `target/quality-35-clean` / `target/quality-35-loss5`。
5 秒固定种子的多频谐波 + 包络 + 少量噪声，500 个输入帧。APM 全关的结果：

| 配置 | 包频带 | 编码实测 kbps | IPv4 总计 kbps |
|---|---|---:|---:|
| 24 kbps | 485 帧 Mediumband（6 kHz），15 帧 Narrowband（4 kHz） | 24.086 | 69.686 |
| 32 kbps | 485 帧 Superwideband（12 kHz），15 帧 Wideband（8 kHz） | 32.264 | 77.864 |
| 48 kbps | 500 帧 Fullband（20 kHz） | 47.150 | 92.750 |

全开 APM 时，三档对应 IPv4 总计 69.638 / 77.848 / 93.682 kbps。
干净场景九组均无 PLC、等待、加速和输出削波。
5% 场景（含排空段）每组删除 27 包，记录 46 次 PLC、20 次等待、0 次加速，
输出均为有限值且无削波。PLC 多于丢包的原因是当前末帧丢失时接收缓冲可能
等待至放弃，本工具没有隐藏该尾部行为；真人语句尾音还需单独检查。
这组结果支持“当前配置可能压缩频带”的机制判断，但不证明所有人声的频带相同，
也不证明提高码率已经解决全部听感问题。

## 后续验收和 issue 状态

1. 同一麦克风录正常语音、轻声、辅音/齿音、大声及停顿，保留未经软件处理的参考。
   打乱 24/32/48 kbps 文件顺序，比较清晰度、自然度、噪声和尾音；单独听 APM 阶段
   以区分降噪吞字与编码失真。补全开但关闭 AGC 的独立对照来归因增益变化。
2. 双机实测及同条件竞品试听；加真实网络抖动、突发丢包、多人同时说话、外放回声。
   重新测 32 kbps + 新 AGC 配置的 CPU 和完整嘴到耳延迟，保留现有红线。
3. 固定经过允许分发的真人语料与基线后，制定频带能量/失真和听感回归判据。
   不用纯音 SNR 或“零欠载”冒充主观音质门禁。
4. issue 中的 `FLAG_DTX`/发包抑制仍单独跟进，不能仅给舒适噪声包加标志就声称
   静默带宽达标；需要验证发包周期、序号/时间戳和接收状态。末帧丢失等待也需跟进。

在完成真人音质验收前不关闭 #35。第一阶段只提交确定的失真修复、候选配置与诊断工具。

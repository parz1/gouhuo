# 2026-10-04 本地多人语音压测

测试对象是 release 构建的真实服务端和 `gouhuo-bot`，通过 TLS 登录、加密 UDP 转发和生产客户端运行层收发。Windows 10.0.26200、16 个逻辑 CPU（AMD64 Family 25 Model 33），服务端和所有机器人共用一台机器。每轮 30 秒，重新启动服务端，不开真实声卡。

可移植的测量元数据与完整汇总见 [JSON 数据](bot-stress-2026-10-04.json)。修改后 9 项机器人测试、1 项汇总回归测试及严格 Clippy 均通过；PowerShell 脚本语法、Rust 格式和 SPDX 检查通过。

这些数据用于定位问题，不是已承诺的服务器人数上限，也没有证明虚拟声卡兼容性。32 / 64 人全发声产生 N×(N−1) 条接收音频流，机器人端的解码和线程调度会干扰服务器。

## 先修复测量工具

最初合成声卡复用 1.5 ms 自旋的精确节拍器。8 人干净网络下机器人约用 300% 单核 CPU，32 人约 1342%；64 人突发登录还触发了服务端 32 条待认证连接保护。第一轮数据保留在 `target/bot-stress/20261004-034353-8b418e6c`，其中 64 人并未完成有效压测。

改为绝对截止时间的睡眠计时，迟到则跳过节拍；新增默认 100 ms 的登录间隔，`--ramp-ms 0` 可独立测试突发登录。新增 `--speakers N` 区分发言者和收听者。UDP 代理增加数据报字节计数，测量脚本记录服务端和机器人各自的资源占用。

所有场景代理队列溢出与代理发送错误均为 0，`RetryVoice` 均为 0。64 人干净网络有一个机器人报告 `audio shutdown did not finish`，进程退出码为 1；其余场景退出码为 0。退出码为 0 不意味着语音稳定，32 / 64 人的结束状态和欠载已经说明失败。

8 人干净网络的上行 / 下行数据报速率约 0.702 / 4.904 Mbps，服务端 / 机器人峰值私有字节约 3.87 / 9.43 MiB。32 人干净网络分别约 2.807 / 18.033 Mbps、10.81 / 67.70 MiB；64 人为 5.464 / 13.750 Mbps、19.95 / 153.24 MiB。高人数的下行没有随理论转发量增长，不可从这些同机数据推出服务器真实转发上限；尚未区分调度饥饿、服务端接收队列丢包、客户端处理不足等路径。

64 人干净网络下服务端峰值私有字节 19.56 MiB、机器人 49.95 MiB，上行 / 下行约 0.182 / 11.032 Mbps。九种场景均正常退出，所有机器人最终 UDP 正常且收到过可听音频，没有代理溢出、代理发送错误、TCP 重连或语音重试；每个机器人的音频只打开一次。8 人丢包场景有一次失联 / 恢复通知，未触发重建。即使干净网络仍有欠载，不能据此声称音质零卡顿。

三种上行中断场景分别记录 8、32、64 次失联并全部恢复。中断结束后最慢恢复时间分别为 1.134、1.144、1.153 秒，按每个机器人的语音启动时钟计算；“被判失联到恢复”的时间不包括前期探测窗口，不能当作整个中断持续时间。

同机测试表明发言者数量显著影响机器人端开销。要确定服务端本身的高并发边界，还需要把负载分布到多台机器，记录服务器内核 UDP 丢包和实际转发失败，并延长运行时间。本轮没有更改生产音频调度、抖动缓冲或服务器保护阈值。

## 测量口径与复跑

丢包场景每个方向 5% 丢包，单向延迟 30 ms、标准差 10 ms 的高斯抖动，种子 42。中断场景按每个机器人语音启动后的第 5–17 秒丢弃上行 UDP，TCP 保持连接。每个机器人启动时间不同，中断并非全局同时发生。

```powershell
cargo build --release -p server -p test-bot
./scripts/bot-stress.ps1 -Counts 8,32,64 -Seconds 30
./scripts/bot-stress.ps1 -Counts 8,32,64 -Speakers 2 -Seconds 30
python scripts/summarize-bot-stress.py target/bot-stress/实际运行目录
```

资源每 500 ms 采样，峰值内存是采样峰值，CPU 不除以逻辑 CPU 数。UDP 速率使用各机器人第 5–25 秒同一代语音实例的计数差：上行送达、下行接受；包括加密数据报开销，不含 TCP、IP / UDP 头。尚未发送的代理排队数据、跨实例切换前未采到的尾部计数不在汇总内。服务端内核队列丢包与发送错误没有直接埋点，代理零溢出不能证明整条链路零丢包。

运行目录包含随机邀请码和服务端证书，应留在本地；报告与汇总不包含这些内容。Git HEAD、二进制 SHA-256 和机器信息在每轮 `metadata.json` 中；本次测量是在未提交的工作树上编译，不能把记录的 HEAD 当成二进制完整源码版本。后续脚本也会记录工作树是否有改动。

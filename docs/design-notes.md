## 名字

### 为什么不叫「开麦」

第一版叫开麦，理由是「名字就是这软件干的事，不用解释」。那条理由是真的，
而且零解释是最难得的一项 —— 但它换不回三个问题：

1. **它是日常黑话，跟语言本身抢搜索。** 「你开麦啊」「麦没开」满互联网都是
2. **语法上跟自己打架。** 代码里真的出现过「然后重开开麦」这种句子
3. **时刻对不上时长。** 「开麦」是一个瞬间动作，而这个产品的全部卖点是
   常驻几小时。语音产品该按「地方」命名，因为你是待在里面

英文标识用拼音 `gouhuo`，不用 `bonfire`：GitHub 上 bonfire 有 1.9k 个仓库
（含一个 944 star 的活跃联邦社交网络，和一个 87 star 的 Discord 客户端重写），
crates.io 上 `bonfire` 已经被占。更要紧的是 `bonfire://` 这个 URL scheme ——
Windows 上协议处理器是谁后写谁赢，撞了之后用户点邀请链接可能打开别的程序，
而那是「一键加入」的唯一入口。日语罗马化 `kagaribi` 也不行：那是日本关东
头部的任天堂明星大乱斗赛事系列。`gouhuo` 在 GitHub 和 crates.io 上都是空的。

**当前进度：M1、M2 完成，端到端实测 91.8 ms，在 120 ms 产品线内。
M3 进行中：一键加入的密码学基础已经做完（身份 + 邀请链接）。还没有 UI。**

## M3 进展：一键加入的密码学基础

痛点 #1（加服务器要手输 IP 和端口）和 #3（身份是本地文件换机就没了）的答案。
这两件事在实现上是同一块：都是「一串能复制粘贴的东西」。

### 邀请链接

```
gouhuo://j/040dn3ypdknqx36hpsp8h9qhmndd9z7221v6ytb3cmq6evvecxm7at9ecdq6phg
```

74 个字符，一行发得出去。自包含**连上去需要的一切**：地址、端口、
服务端证书指纹、可选的邀请码。

**必须自包含**，因为「可自部署」意味着不能有一个所有人都依赖的中心短链服务。

**必须带证书指纹**，因为自部署的服务端只能自签名，不固定证书的自签名 TLS
等于没有认证。这两件事合起来正好：**用户体验上的「一键加入」和安全上的
「证书固定」是同一个动作** —— 用户粘一串东西进去，既省了手输 IP，
也完成了信任建立。

编码用 Crockford base32（字母表里没有 `i` `l` `o` `u`，解码时 `I`/`l` 当 `1`、
`O` 当 `0`），末尾两字节校验和。所以：复制漏一截会**当场报错**，
而不是解析出一个看起来对的地址。

### 身份

一对本地生成的 Ed25519 密钥，公钥即身份。没有注册、没有密码、没有找回流程，
也没有任何中心服务器知道你是谁。

代价很直接：**私钥丢了身份就没了。** 所以导出导入不是附加功能：

```
gouhuo-secret-v1-<base32>
```

前缀故意写得吓人，用户一眼就知道这串不能随便发。

磁盘上用 **Windows DPAPI** 加密：密文绑定当前 Windows 账户，文件被网盘同步走、
被备份带走、被信息窃取器抓走，在**别的机器上都解不开**。全程零交互，
不用用户设密码，符合「装完即用」。

它挡不住什么也写清楚了：同一账户下运行的程序照样能解密。DPAPI 防的是
「文件被搬走」，不是「本机被攻陷」。后者要用户设密码才能解，而那违背「装完即用」。

另一个后果：**重装系统或换 Windows 账户之后旧文件就解不开了**，所以首次生成
身份时必须提示用户导出备份 —— `load_or_create` 的返回值里专门带了这个标志。

### 控制面消息：protobuf

定义在 [`crates/protocol/proto/control.proto`](crates/protocol/proto/control.proto)，
两端共用生成的类型，别的语言写第三方客户端也照着这一份。

选 protobuf 的理由是**自部署下版本一定会不一致** —— 没人会同时升级公会的服务器和
自己的客户端。加字段不能破坏旧端，这正是 protobuf 的演进语义解决的问题。
而且这是暴露在公网上的解析器，处理不可信输入，手写的攻击面明显更高。

用 protox 编 `.proto`（纯 Rust），**不需要装 protoc** —— M2 在 meson/ninja 上
已经吃够外部构建工具的苦头了。

两个刻意的协议决定：

- **线上传的是角色，不是权限矩阵。**「权限是个矩阵没人看得懂」是要修的痛点之一，
  所以 `Role` 就四档（访客/成员/频道管理/管理员）。服务端自己决定每档能干什么，
  客户端只要知道「我是什么角色」就能把界面画对。逐项配权限是服务端的事，不进协议
- **文字消息只有纯文本。** 富文本在明确不做的清单里 —— 场景是边打游戏边说话，
  文字是用来发个链接报个坐标的，不是用来排版的

分帧是 4 字节大端长度 + protobuf 字节，**长度有上限**（1 MiB）。
先判上限再判够不够 —— 反过来的话，对端声称 4 GB 时我们会一直等、缓冲区一直涨，
等于让对端决定我们用多少内存。

### 信任链：一跳，端到端测过

```
发邀请链接的人  ->  链接里的证书指纹  ->  TLS 握手  ->  UDP 密钥
```

1. 服务端自签一张证书并**持久化**。重启换证书 = 之前发出的所有邀请链接全部失效，
   而那些链接可能已经躺在几十个人的聊天记录里，所以 `load_or_create` 是默认路径
2. 客户端比对指纹 **并且** 验 TLS 签名
3. 语音密钥用 TLS 的 key exporter（RFC 5705）从这条连接里派生，**不另起握手**

**第 2 步里"并且"那两个字是要命的。** 网上大量的「跳过证书校验」示例是所有方法
都返回 `Ok`，改成「比对一下指纹」看着就安全了——并不是：证书是**公开**的，
只比指纹不验签名的话，中间人把真证书原样转发过来就能冒充服务端，**根本不需要私钥**。
`verify_tls12_signature` / `verify_tls13_signature` 必须老实交给底层密码库。

指纹比对回答「是不是这一台」，签名校验回答「对面是不是真的持有那把私钥」——
后者替代不了也省不掉。

反过来，**有效期和主机名是刻意不看的**：这里没有 CA，撤销的唯一手段是换证书重发
链接，有效期帮不上忙却能制造「某天所有人突然连不上」；而服务器可能是裸 IP、
内网地址、动态域名，要求证书里的名字对得上只会徒增失败。

不用 Noise 而是从 TLS 派生，理由是**少一套要审的东西**：那条连接本来就完成了
双向认证，再来一套握手换来的是同一件事。

端到端测试跑的是真 TCP、真握手：指纹对得上就连上、不对就报「有人在中间」、
两条连接派生出不同的密钥、一条邀请链接能驱动整个连接过程。

### 服务端：一个二进制，跑起来就能用

```
GOUHUO_DATA=./data gouhuo-server
```

没有配置文件。第一次启动自己生成证书和邀请码，然后把邀请链接打在屏幕上 ——
把那一行发给朋友就完事了。要调的东西全走环境变量（`GOUHUO_PORT` /
`GOUHUO_DATA` / `GOUHUO_HOST` / `GOUHUO_INVITE` / `GOUHUO_MAX_USERS`）。

分两层，界线是**有没有 IO**：

- `state` —— 纯状态机。频道树、谁在哪儿、谁能进来。不碰 socket、时钟、密码学
- `conn` —— TLS、线程、分帧、验签。只把字节搬进搬出，然后翻译成对 `state` 的一次调用

这条线的代价是 `conn` 里要写一堆转接代码；换来的是「服务器满了之后管理员还进不进
得来」这种问题，答案在一个 20 行的函数里，而不是散在七个 await 点之间。

**用线程，不用 async。** 3–20 人的频道、一台机器撑一个社群，几十条连接封顶；
这个量级上 async 换不来任何东西，却要带进四十来个依赖，跟「单二进制、自部署零
依赖」直接冲突。真到了要换的那天，改的是 `conn` 一个文件，`state` 一行都不用动。

同样的理由，`voice-core` 的 APM 被拆成了 feature：服务端只转发 Opus 包，
从头到尾不碰音频采样，带上 APM 只是白白多编几个 crate、多占体积。

认证是三个来回：`Hello` → `Challenge`（服务端出随机数）→ `Authenticate`
（签那个随机数）→ `Welcome`。**随机数必须服务端出** —— 让客户端自己选要签的内容
等于允许重放，抓一次签名就能无限次冒充。

已经钉住的规则，全部有端到端测试（真 TCP、真 TLS、真 Ed25519）：
签名验不过进不来、邀请码不对进不来、文字消息的发送者和时间戳一律由服务端盖章
（客户端填的作废，否则谁都能冒充别人说话）、重名自动加后缀、同一把钥匙再连一次
顶掉旧连接而不是变成两个人、认不出来的消息忽略而不是断开、连上来不说话的连接
会被握手超时清掉。

### 语音转发：服务端解密再加密

语音密钥是**每条连接**从 TLS 里派生的（RFC 5705 exporter），收发两端的密钥不同，
所以转发不可能是原样复制 —— 服务端要解开再用收方的密钥重新封上。
上下行各派生一把，省掉「转发给 A 的包其 session 永远不等于 A 自己」这条
散落在别处、容易被重构破坏的 nonce 唯一性论证。

另一条路是全频道共享一把密钥，服务端只管搬字节，更快。没选它是因为有个洞：
所有成员都拿着同一把钥匙，**任何人都能伪造别人的 session id**，
做出「某人正在说话」的假象，服务端分辨不出来。每连接一把密钥之后，
AEAD 的 tag 本身就是发送者的证明。代价是每包一次解密加 N 次加密 ——
ChaCha20-Poly1305 在几十字节的负载上是纳秒级的，20 人全说话每秒两万次，
对一台自部署的小机器不构成问题。

（`protocol` 里原来写着「服务端不解密负载」，那是共享密钥方案的假设，已经改了。）

### 只听不说的人也要能听见

服务端的 UDP 地址是从收到的包里**学**来的 —— NAT 会改源地址，事先不可能知道。
直接的后果是：一个从不说话的人，服务端永远不知道往哪儿发给他，他会完全听不见声音。

所以有保活包（`FLAG_KEEPALIVE`）：负载为空，不转发给任何人，服务端收到原样回一个。
它同时回答了「UDP 到底通不通」—— 一直收不到回包就说明被挡了，该退回 TCP 传语音。

学地址这件事本身也有个坑：**必须先验签再学**。反过来的话，任何人伪造一个包
就能把别人的语音重定向到自己那里 —— 一次不需要任何密钥的窃听。

### 超时不用 SO_RCVTIMEO，用看门狗

M1 在 UDP 上被 `SO_RCVTIMEO` 坑过一次：读超时跟到达的数据撞车时会**丢数据**。
同一件事在 TCP 上一样成立，只是表现为流错位，更难查。

所以服务端的读永远是阻塞的、没有超时；另起一个看门狗线程看谁多久没动静了，
该踢的直接 `shutdown` 那条 socket —— 阻塞的读会立刻返回 0。

### 默认端口不在 49152 以上

「动态/私有段」听起来正是给自定义服务用的，其实恰恰相反：那是各系统的临时端口段。
Windows 上更糟，Hyper-V / WSL / Docker 会在那段里成片地做保留 ——
本机实测 UDP 的 49409–49908 一整片都被占了，绑上去直接 WSAEACCES。
**Mumble 的 64738 正落在这一片里。**

篝火要求 TCP 和 UDP 用同一个号（用户只记一个数，转发也只转一次），所以要挑一个在
所有系统临时段之下的：Linux 是 32768–60999，Windows / macOS 是 49152–65535，
取交集就是「小于 32768」。默认落在 **20800**。

绑不上时的报错会直接把 `netsh int ipv4 show excludedportrange` 那条命令给出来 ——
系统默认那句「以一种访问权限不允许的方式……」一个字都没提真正的原因，
而用户正好就卡在这一步。

### 一个测试抓到的真 bug

`trimmed[..PREFIX.len()]` 这个写法在中文输入上会 panic：`len()` 是字节数，
切片也按字节切，用户往邀请码框里粘一段中文，长度检查轻松通过（一个汉字三字节），
然后切在字符中间 —— 客户端直接崩。

而邀请码和身份导入这两个框，**正是最容易被粘进中文的地方**
（「你发我的那个码呢」）。修在 `protocol::text` 一处，两个解析器共用，
两边都加了中文和 emoji 的回归测试。

## 客户端：界面

界面提前做了，没等 M3 全做完。原因是**权限模型应该在有界面之后再定** ——
痛点 2 是「权限是看不懂的矩阵」，而在没有界面的情况下设计预设角色，
正是做出那种矩阵的标准路径：你会不断加正交的开关，因为没有任何东西逼你
把它们收敛成四个词。

分两层，跟服务端同一条界线：

- `client-core` —— 连接、认证、状态镜像。**不含任何界面**，所以它能直接
  对着真服务端跑集成测试：「点了切频道，别人那边看到了吗」不用打开界面就能回答
- `client` —— Slint 界面。只把 `client-core` 的状态画出来，把点击搬回去

一条连接两个线程：读线程阻塞读 TLS 并更新名单，心跳线程每 5 秒发一次 Ping。
**界面线程既不读也不写 socket** —— 界面卡住不会掉线，网络卡住也不会冻住界面。
后者是必须的：网络一出问题，用户第一件想做的事就是点「离开」。

### 为什么是 Slint 不是 Tauri

安装包 60 MB 和常驻内存这两条红线**完全由界面框架决定**，拖到最后才发现
就来不及换了。所以框架一定下来就量：

| | 实测（dist profile） |
|---|---|
| 冷启动到窗口出现 | 79 / 92 ms（首次 220 ms，磁盘缓存冷） |
| 空闲常驻内存 | 59.4 MB |
| 客户端可执行文件 | 12.5 MB |
| 服务端可执行文件 | 1.4 MB |

作为参照，Electron 系的语音软件光界面进程就要两三百 MB，冷启动按秒算。
Tauri 会好一些，但它依赖 WebView2 —— 界面行为要看用户机器上装的是哪个版本，
而这对一个要「装完就能用」的软件是个不该有的变量。

客户端那 12.5 MB **还不是安装包**：音频那半边（Opus + APM）
还没链进去。记在 `redline.rs` 里是为了让它涨的时候看得见。

### 一键加入

命令行上给一个 `gouhuo://` 链接就直接连 —— Windows 的协议处理器就是这么
调起来的，所以这一个参数同时也是「点链接进频道」的落点。

**第一次跑的人不自动连**：那时候昵称还是 Windows 用户名，身份也是刚生成的，
该让他先看一眼再进去，否则他会顶着 `admin` 出现在一屋子人面前。

### 语音链路：端到端 36.7 ms，实测

```text
采集 ──► APM ──► Opus ──► 加密 ──► UDP ─┐
                                         │  服务端转发
播放 ◄── 混音 ◄── Opus ◄── 抖动缓冲 ◄────┘
```

把两头的声卡抽成 trait 之后，整条链路能在没有声卡的机器上跑 —— 于是可以
喂一个啁啾进去、从另一头捞出来做互相关。**这是第一次真正量端到端**：

| | |
|---|---|
| 实测（不含声卡和 APM） | **36.7 ms** |
| 理论下限（分帧 + 编码器前瞻 + 抖动缓冲） | 36.5 ms |
| 相关峰值 | 0.975 |

只比理论下限大 0.2 ms —— **链路里没有任何一处藏着多余的缓冲**，这正是要验的。

M1 的 46.5 ms 和这个 36.7 ms 是两回事：前者注入过网络损伤（同城档）、而且是把
编解码和抖动缓冲单独搭起来测的，中间没有真服务端也没有真加密；后者是本机回环
（网络时间≈0）但整条真的接起来。两个都有用 —— 一个告诉你网络占多少，
一个告诉你我们自己占多少。

真声卡那条路另有一个测试（`--ignored`，因为 CI 上没有音频设备），
实测 5 秒发出 494 个包（100/秒，正好是 10 ms 帧）、0 欠载、往返 0.277 ms。

### 三个线程，时钟全部来自设备

发送阻塞在采集上，接收阻塞在 recv 上，播放阻塞在渲染上。**没有一处用 sleep
凑节拍。** 声卡有自己的晶振，跟系统时钟差几十 ppm 是常态；自己数着时间喂数据，
几分钟之后必然积累出一次溢出或欠载，听感上是周期性的爆音。

帧长全程写死 10 ms：APM 只接受 10 ms，Opus 也支持，全链路同一个帧长直接消掉
一整类「这里攒一点那里补一点」的缓冲代码 —— 那种代码正是延迟悄悄变大的来源。

### 不说话的时候一个包都不发

松开按键（或 VAD 判定没人声）之后，先补一个带 `FLAG_TERMINATOR` 的包让对面
立刻收尾，然后只留每两秒一次的保活。静默带宽因此是 57 字节 / 2 秒 ≈ **0.23 kbps**。

### APM 默认开着，但仍然可选

回声消除和降噪是「外放开黑不啸叫」的全部依据，所以客户端**默认带着它**，
`git clone` 完 `cargo run` 跑出来就是完整的。

它仍然是个 feature，是为了服务端：那边只转发 Opus 包，从头到尾不碰音频采样。

> M2 时它是默认**关**着的，因为当时那套 C++ 工具链挡在「git clone 完
> cargo build」前面。换成纯 Rust 之后这个理由没了 —— 一个卖点功能
> 不该要用户自己去开。见 [`docs/apm-backend.md`](docs/apm-backend.md)。

### 全局热键：Raw Input，不是钩子

按住说话要在游戏全屏时也管用。三条路，选了第三条：

- **`RegisterHotKey`**：最省事，但它**把按键吃掉**（注册了 `V`，游戏就收不到
  `V` 了 —— 而玩家常把说话键同时绑着游戏里的功能），而且走焦点窗口那条路径，
  很多全屏游戏下根本不触发。
- **低级键盘钩子**：能收全、也能不吃掉，但它是**系统级注入**：每一次按键都要
  过我们的回调，我们慢一下全系统的输入就卡一下。而且它是反作弊最敏感的那类
  行为之一 —— 一个开黑软件不该让人担心会不会因此被封号。
- **Raw Input（`RIDEV_INPUTSINK`）** ✅：没有焦点也收，不吃按键，不注入任何
  东西，也不在别人的输入路径上。代价是要有一个窗口和一个消息循环，
  用 `HWND_MESSAGE` 建个纯消息窗口就行。

鼠标侧键一起收 —— 绑侧键说话在玩家里极其常见，Raw Input 里这只是多注册一个
用途页的事。

按键名字有几类是 `GetKeyNameTextW` 处理不好的，自己给：左右 Ctrl/Shift/Alt
（它对左右给同一个名字，而绑「右 Alt」和「左 Alt」是完全不同的选择）、
**F13–F24**（正常键盘上没有，所以拿不到名字，但它们恰恰是按住说话的最佳
选择 —— 不跟任何东西冲突）、小键盘（跟主键盘那排数字分不开）。

### 默认是语音激活，不是按住说话

默认按住说话的话，没绑键的新用户会发现怎么说都没人听见，而且完全不知道为
什么。所以默认语音激活，改成按住说话之后没绑键会当场警告。

### 设置文件是手改的

一行一个 `键=值`，跟身份文件放在一起（搬机器一起走）。不用 JSON/TOML 是因为
就这么几个值不值得拉一个序列化库，而且**这个文件用户会手改** —— 自部署这群人
遇到问题的第一反应就是打开配置文件看看。

认不出来的行直接跳过。偏好设置坏了绝不能让客户端打不开。

### 试听自己的麦

设置面板里一条电平条 + 一个「试听」开关，回答「找人试之前我怎么知道麦克风好不好使」。

**电平条上画着语音激活的阈值刻线。** 这是它存在的全部理由 —— 用户最常问的
「我说话了为什么没触发」，看一眼就知道是**没收到音**还是**收到了但没过线**。

**不连服务器也能试。** 「我的麦克风好不好使」这个问题，恰恰在连不上的时候
最想知道：是我麦克风坏了，还是服务器的问题？所以登录页上就有「先试试麦克风」
这个入口，设置是一整页而不是连上之后才有的侧栏。

试麦走的是 `voice-core::miccheck`，只开采集和播放两个线程，完全不碰网络。
没有复用 `pipeline` 是因为那个要 session id、服务器地址和两把密钥 ——
硬凑就得给它假地址假密钥再往死地址发包，不如另写六十行。两边的电平算法
是同一个函数，不然用户会发现「试麦时条子动，进了频道就不动了」。

试听走的是**直连**，不过编解码。过一遍 Opus 能听到「别人听你是什么效果」，
但要多等抖动缓冲那 20 ms，加起来六十多毫秒 —— 延迟听自己说话超过 50 ms 会明显
干扰发音（延迟听觉反馈），用户会以为是软件有回声。试听要回答的是
「麦克风好不好使、增益够不够、有没有噪音」，直连够了。

### 设备选择不是锦上添花

这台开发机上实测（`cargo test -p voice-core --lib device_scan -- --ignored --nocapture`）：

| 设备 | 峰值 |
|---|---|
| SteelSeries Sonar - Microphone（虚拟） | −120.0 dB（纯数字静音） |
| 麦克风 (Arctis Nova Pro Wireless) | −108.3 dB |
| 耳机式麦克风 (Arctis GameBuds) | −120.0 dB |
| 麦克风 (Steam Streaming Microphone) | 44100 Hz，这一版不支持 |
| 麦克风 (2- Insta360 Link 2C) | −120.0 dB |

**系统默认的那个是 SteelSeries Sonar 的虚拟麦克风，纯静音。** 这正是
`wasapi/mod.rs` 一开始就预言过的情况：玩家机器上虚拟声卡极其常见，
而它们没在路由的时候什么都收不到。所以：

- 界面上标出哪些是虚拟声卡（看总线枚举器名，不是猜名字）
- 用的是虚拟设备时直接点名警告
- 存下来的设备 id 失效时**退回系统默认**而不是就此没声音 ——
  用户拔个耳机而已，他不会想到要去设置里重选一遍

条子一直不动时的提示里还写了第三种原因：**Windows 的麦克风隐私设置**。
被它挡住的时候应用拿到的是**静音而不是报错**，看起来跟设备坏了一模一样。

### 采样率交给 Windows 转

共享模式默认必须用引擎的混音格式，而那个格式**由用户在 Windows 声音设置里
决定**。第一版直接拒绝非 48 kHz 的设备，理由是「现在的 Windows 默认基本都是
48 kHz」。这个假设在一台真实的玩家机器上当场破了：

| | |
|---|---|
| 默认扬声器 | SteelSeries Sonar - Gaming，**96000 Hz** |
| 一个麦克风 | Steam Streaming Microphone，**44100 Hz** |

那台机器**开箱就是用不了的**。现在用 `AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM`
让音频引擎自己插重采样器，13 个播放设备全部能打开。代价是它那一段的延迟 ——
比「不支持」好太多。

探针（M1/M2 量设备延迟的那些）**不开这个**：它们要量的正是设备原生的表现，
中间多一个重采样器就不是那个数了。

### 播放坏了不该把采集拖死

上面那个 96 kHz 的扬声器还牵出一个更糟的设计错误：试麦的两个线程原来是
**连坐**的，播放那边一死，采集也跟着停。表现是「麦克风灯闪一下就灭」，
而界面上什么都不说 —— 因为设备错误当时只在「已连接」那个界面里渲染，
设置页上看不见。

两条都改了：播放挂了只报「听不到声音（麦克风电平不受影响，还能看）」，
采集继续跑；错误在哪一页发生就在哪一页显示。

看电平根本不需要扬声器 —— 而「我的麦克风有没有在收音」恰恰是用户最想
知道的那件事。

### 「挨个试一遍」

对着一个下拉框，用户是猜不出来哪个麦克风能用的 —— 而程序挨个打开试一遍
只要几秒钟。所以设置里有个按钮，一键把每个麦克风都开 1.2 秒，报回三档结论：

| 结论 | 意思 | 下一步 |
|---|---|---|
| 听到了（−25 dB） | 收到人声了 | 就用它 |
| 只有底噪（−99 dB） | 设备在工作，但没收到人声 | 静音键？隐私设置？麦克风没对着嘴？ |
| 纯静音 | 一个非零样点都没有 | 这个设备根本没在路由 |

这三档的界线是实测定的，不是拍的：纯数字零正好是 −120（`frame_db` 的下限），
真硬件的底噪在 −100 上下，正常说话在 −30 到 −15。中间空得很开。

分清「底噪」和「纯静音」很重要 —— 它们的下一步完全不一样，而在一个
只会说「没声音」的界面里，用户永远分不出来。

### APM：回声消除实测

```bash
cargo test -p voice-core echo:: -- --nocapture            # 合成的线性回路
cargo test -p voice-core acoustic -- --ignored --nocapture # 真音箱真麦克风
```

| | 合成（线性回路） |
|---|---|
| 回声抑制 | **57.9 dB**（残留绝对电平 −82.0 dB） |
| 没有回声时对人声的损伤 | **1.1 dB** |

**合成的数字不能当产品表现看** —— 那条回声路径是纯线性的（延迟 + 衰减），
而真正区分 AEC 好坏的是音箱的非线性失真、时钟漂移、房间混响。真声学往返
的测试也写了，但这台机器上的麦克风都自带噪声门，量不出可信的数 ——
经过见 [`docs/apm-backend.md`](docs/apm-backend.md)。

第二条比第一条更要紧：绝大多数人戴耳机，根本没有回声。开了 AEC 反而把他的
声音削掉一截的话，这个功能就是负收益。

#### 量这个数字踩了四个坑，每一个都让结果虚高或虚低

1. **信号越界。** 第一版的噪声生成器能冲到 ±2000（0 dB 就是满刻度），
   量出来 54.6 dB。测试照样过 —— 但那个数字是假的。
2. **回声太轻。** 修正电平之后回声只有 −32 dB，离 AEC3 的残留底噪（−50 dB）
   只剩 17 dB，量出来的是底噪而不是 AEC 的本事。按真实音量（−24 dB）重来。
3. **高通滤波器混进来了。** 测试信号里有个 84 Hz 的分量，正好在高通的刀口上。
   `echo_in` 在滤波前取、`mic_out` 在滤波后取，于是高通滤掉的那部分被算成了
   AEC 的功劳。把信号搬进人声频段之后，30.2 dB 掉到 2.9 dB。
4. **纯音是退化激励。** 2.9 dB 又是另一个极端 —— 我那个「类语音」信号其实
   以两个正弦为主，而正弦只激发两个频点，自适应滤波器在别的方向上无从学起。
   换成带限噪声 × 音节包络（真语音的样子）立刻就是 26 dB。

四次里有三次，错误的方向是**让结果更好看**。

#### 双讲没量

试过，量不出有意义的数字：合成的近端和远端在 AEC3 眼里是同一种东西
（同样的带限噪声、同样的音节包络），抑制器分不开，把两个一起压到残留底噪 ——
得到的是测试信号的性质，不是 AEC3 的性质。

真要量得用 ITU-T G.168 那样的标准测试集，或者干脆戴上耳机找个人说话。
在那之前，与其报一个站不住的数字，不如明说没量。

### 报错要能照着做

连不上的时候只给一句 `Connection refused`，用户唯一能做的就是去问发链接给
他的那个人 —— 而那个人也不知道。所以每条错误都要回答两件事：**发生了什么**、
**现在该做什么**。有测试钉住每个分支两样都不能缺，也不能漏出 `os error`
这类只有程序员看得懂的东西。
